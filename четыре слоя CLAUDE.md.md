- Одна из [теорий заполнения CLAUDE.md](теории%20CLAUDE.md.md): четыре слоя — сжатие знаний, правила, декларация возможностей, лабораторные заметки.
	- По сути — чек-лист «о чём не забыть». Два слоя работают как есть, два — с оговорками.
- Сжатие знаний
	- Краткая карта проекта: структура, ключевые файлы, команды. То, что генерирует `/init`.
	- Экономия относительная: Claude меньше ищет по проекту, но сам файл уходит в каждом запросе.
		- Выгода есть, пока описание короткое.
	- Карта устаревает. Неверная структура вредит сильнее, чем никакой: Claude ей поверит.
- Правила
	- Стек, стиль кода, как реагировать на ошибки.
	- Основной слой, работает как есть.
- Декларация возможностей
	- Идея: какие инструменты Claude может использовать сам.
	- Буквально — не работает: `CLAUDE.md` не выдаёт разрешений.
		- Разрешения — `allow`/`deny` в [settings.json](_settings.json.md), серверы — в настройках [MCP](MCP.md).
		- «Можешь сам запускать миграции» в `CLAUDE.md` — промпт разрешения всё равно появится.
	- Работает как подсказка, какой инструмент выбрать — по сути, те же правила.
		- «Для GitHub — `gh`».
		- «БД смотреть через MCP postgres, а не `psql`».
		- «Линтер — `make lint`, не ruff напрямую».
- Лабораторные заметки
	- Идея: журнал удачных и неудачных попыток, чтобы не повторять ошибки.
	- Как журнал в `CLAUDE.md` — плохо: он растёт, а весь файл грузится в каждый запрос.
	- Сырой журнал — в [auto-memory](auto-memory.md) (виды `feedback`, `project`) или в отдельный файл, который Claude читает по необходимости.
- Советы
	- Пользоваться схемой как чек-листом при ревизии `CLAUDE.md`: каждого ли слоя хватает, нет ли лишнего.
	- В карту проекта писать то, что меняется редко и не видно из кода.
	- Из неудачной попытки выжимать правило: не «пробовали X — упало», а «не делать X, потому что Y; делать Z».
	- Возможности, которые Claude должен использовать без вопросов, — разрешать в `settings.json`, а в `CLAUDE.md` только объяснять, когда что брать.
